Нужно сделать консольную утилиту на Node.js + TypeScript для замера скорости скачивания по HTTP/HTTPS (10 последовательных запросов к заданному URL с замером среднего времени, общего объёма и скорости). Сделай решение уровня продакшн-CLI: чистое, надёжное и расширяемое, без оверинжиниринга.

Стек и ограничения:
- Node.js (ESM), TypeScript со строгими флагами (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` и т.п.).
- Минимум рантайм-зависимостей — сеть на нативных `node:http`/`node:https`, терминальный UI на чистых ANSI-последовательностях без тяжёлых TUI-библиотек.
- Инструменты качества: ESLint (strict TypeScript rules, запрет `console.*` в пользу явных потоков вывода и `any`), Prettier, Vitest.

Архитектура и стиль кода:
- Раздели приложение на чёткие слои по SOLID и принципам DI (через интерфейсы и композицию в entrypoint): CLI/App, Config/Validation, Network, Core (движок бенчмарка и расчёт метрик), TUI, i18n.
- Именование файлов и сущностей в едином стиле а-ля Angular/NestJS (`feature.role.ts`, например `benchmark-engine.service.ts`, `cli-parser.service.ts`).
- Никаких магических чисел и сырых escape-строк по коду — ANSI-последовательности, управляющие символы, дефолты и токены флагов держи в отдельных константах.
- Пиши аккуратный JSDoc на интерфейсах, их полях и публичных методах (`@param`, `@returns`, примечания EN + RU), крупные методы декомпозируй на понятные хелперы.

Что должно уметь приложение:
1. Два режима работы:
   - Интерактивный TUI (если запущено в TTY без `--no-tui`): меню выбора URL из JSON-конфига пресетов или ввод своего URL, живой прогресс по итерациям (прогресс-бар, текущая скорость, статус ретраев), экран итоговой сводки и экран ошибок, переключение языка на лету, корректный выход по `q`/`Esc`/`Ctrl+C`.
   - CLI-режим для скриптов и CI: флаги `--url`, `--iterations` (по умолчанию 10), `--timeout`, `--lang`, `--json`, `--no-tui`, `--help` и валидация входных параметров. Декларативный реестр флагов без лапши из `if/else`.
2. Сеть и надёжность:
   - Потоковое чтение ответа (`Stream`) без буферизации всего файла в память (чтобы не падать на тяжёлых файлах).
   - Поддержка редиректов (с ограничением глубины), таймаута на запрос и отмены через `AbortController` (по `SIGINT`/выходу из экрана).
   - Политика ретраев: для `429` с учётом заголовка `Retry-After`, для транзиентных сетевых сбоев и `5xx` — exponential backoff с джиттером.
3. Метрики:
   - Используй `performance.now()` / высокоточный таймер. Считай общее время, среднее время запроса, мин/макс, общий объём в байтах/МБ, среднюю и пиковую скорость (Mbps и MB/s — обязательно поясни единицы в коде и README).
4. TUI без мерцания:
   - Альтернативный буфер терминала, скрытие курсора, восстановление состояния терминала при выходе или падении.
   - Дифференциальный рендер (перерисовывать только изменившиеся ячейки/строки, а не чистить весь экран каждый тик).
   - Динамическая вёрстка колонок в сводке от максимальной длины подписей, чтобы длинные фразы (особенно на русском) не обрезались и не наезжали на значения.
5. Локализация (RU/EN):
   - Простая расширяемая система на словарях (`Locale` enum с возможностью передать строковый код + fallback на дефолтную локаль), без громоздких схем.
   - Рядом с вызовами `i18n.t(...)` оставляй короткий комментарий с русским текстом для быстрого чтения кода.

Тесты, документация и проверка:
- Напиши адекватные unit-тесты на Vitest для ключевой логики: расчёт метрик, retry-стратегии, CLI-парсер, валидатор URL, i18n (включая проверку консистентности ключей RU/EN), буфер/дифф-рендерер, ключевые сценарии движка и TUI.
- Сделай понятный `README.md`: описание возможностей, установка, примеры запуска (интерактивно, по URL, JSON-вывод), объяснение единиц измерения скорости и архитектуры.
- Перед финальным ответом обязательно сам прогони `typecheck`, `lint`, `format:check`, `test` и сборку `build`, плюс проверь запуск собранного CLI с `--help`.
